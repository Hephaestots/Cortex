## Read slices (2026-11-18)
`GetQuestions` is written, tested by hand and committed. `GetQuestionById` is written and builds, not committed yet (see "Repository state").

### `GetQuestions`

- **One list endpoint with filters, not one endpoint per filter.** "Questions by tag" is `GET /api/questions?tags=x`, not `/api/tags/{slug}/questions`. A tag narrows the same collection, filters combine (`?bookId=`, `?sort=` later), and it is what the Stack Exchange and GitHub APIs do. Nested routes are kept for real ownership (`/api/questions/{id}/answers`). A tag page that needs the tag's own data (name, description, a 404 for an unknown tag) will call `GET /api/tags/{slug}` from the tags slice.
- **Tags filter:** repeated keys (`?tags=a&tags=b`), combined with **AND** (a question must have all of them), normalised with `Tag.Normalize`, duplicates and empty values dropped, at most `Question.MaxTags` (5: with AND, more can never match). Implemented as one `Where(q => q.Tags.Any(t => t.Slug == slug))` per tag, which becomes one `EXISTS` each and uses `ix_question_tags_tag_id`. An unknown tag gives an empty page. Comma-separated values are not split: `?tags=a,b` is the single tag `"a,b"`.
- **Offset paging** (`?page=&pageSize=`, defaults 1 and 20, `pageSize` at most 50), chosen over keyset for page numbers and a total count, and because "top" sorting will page the same way. Costs accepted: deep pages get slower, and inserts can shift rows between pages. Order is `CreatedAt DESC, Id DESC`; the id breaks ties so a row never appears on two pages or none. The count runs on the filtered query before paging (a second query).
- **Shared paging types in `Features/Shared/`:** `PagedQuery` (abstract base for `[FromQuery]` list queries: `Page`, `PageSize`, `Skip`, `DefaultPageSize`, `MaxPageSize`, `MaxPage`), `PagedQueryValidator<T>` (abstract; a query's validator derives from it to get the paging rules) and `PagedResponse<T>(Items, Page, PageSize, TotalCount)` with a computed `TotalPages`. Verified that Wolverine binds the inherited properties and runs the derived validator.
- **Binding:** the query is a class with settable properties and defaults, bound with `[FromQuery]`, so every parameter is optional; Wolverine's FluentValidation middleware validates `[FromQuery]` types too. `opts.RejectUnparseableQueryValues = true` in `Program.cs` turns `?page=abc` into a 400 (by default Wolverine silently keeps the default value; strict becomes the default in Wolverine 7). Query keys are case-insensitive.
- **Responses are EF projections** (`Select(q => new Dto(...))` written inline), not mappers: EF selects only the needed columns, computes `AnswersCount` and `Score` (`SUM` of the vote values) in SQL, and tracks nothing, so no `Include` or `AsNoTracking`. Never call a `From(q)` method inside `Select`: EF cannot see into it and loads the entity without its navigations. `QuestionSummary` has no `Body`.
- **Return type:** `Ok<PagedResponse<T>>` built with `TypedResults.Ok(...)`. No `NotFound` (an empty page is not missing), and the 400 comes from the validation middleware.
- **Reads are public:** no `[Authorize]`, and they must not take `CurrentUser` (it throws without a user).
- **`ViewCount` is not incremented on GET** (open point): a read that writes breaks safe and cacheable GETs. Candidate later: an event, or a separate endpoint.

### `GetQuestionById`
- **First endpoint with a 404:** `GET /api/questions/{id}` returns `Results<Ok<QuestionDetail>, NotFound>`. The list endpoint has no 404, because an empty page does not mean anything is missing; one question that does not exist does.
- **One method, no Load/Handle split:** the split is for endpoints that load an entity and then act on it (update, delete, post answer). In a read, the projection is the load.
- **Projection with `Where(...).Select(...).FirstOrDefaultAsync`**, not `FindAsync`: `FindAsync` loads the tracked entity without its tags or votes, so `Score` and the tag list could not be computed in SQL.
- **Its own response record, `QuestionDetail`, not `QuestionSummary`:** a list row and a detail page change for different reasons. `QuestionDetail` adds `Body`, `AuthorId` (the client compares it with the token's `sub` to show Edit, and later Accept), `ViewCount`, `UpdatedAt` (to show "edited"), and `AcceptedAnswerId` instead of `HasAcceptedAnswer` (a detail page must know *which* answer to mark). `QuestionSummary` stays in `GetQuestions.cs`, its only user.
- **No answers yet (decided 2026-11-18):** they come with the Answers slice (item 7), which first has to settle three things:
  - **Ordering.** Without an `OrderBy`, Postgres returns answers in any order, and the order can change between requests. Candidate: accepted first, then score, then `CreatedAt`.
  - ~~**Author name.**~~ Done 2026-11-20 with `CreateAnswer`: `Answer.AuthorDisplayName`, migration `20261120131957_AddAnswerMissingColumns`.
  - **Row multiplication.** Projecting two collections (tags and answers) in one query returns one row per tag × answer, each repeating the answer body. `.AsSplitQuery()` turns that into one query per collection; alternatively, answers get their own endpoint (`GET /api/questions/{id}/answers`).

## EditQuestion (2026-11-18)
`EditQuestion` (`Features/Questions/EditQuestion.cs`) is written, tested by hand and on the branch `feat/edit-question`.

- **`PUT /api/questions/{id:guid}`, `[Authorize]`, 204 No Content.** Only the title, body and tags can change (decided 2026-11-18): the book and the author stay as created, so `EditQuestionRequest(Title, Body, TagSlugs)` does not carry them, and a `bookId` in the body is ignored. PUT rather than PATCH, because the request replaces all three editable fields; they are all required.
- **First Load / Validate / Handle split.** Per the Wolverine 6 HTTP middleware docs, methods on the endpoint class named `Load`/`LoadAsync`, `Before` and `Validate` run before the main method, their return values become variables the main method takes as parameters, and an `IResult` other than `WolverineContinue.Result()` stops the request with that result.
  - `LoadAsync(id, db)` returns `Question?`, tracked and with `Include(q => q.Tags)`: `Question.Edit` replaces the tag list, and EF can only work out which `question_tags` rows to insert or delete if the current ones are loaded. (Reads project and need no `Include`; writes load the aggregate.)
  - `Validate(Question?, CurrentUser)` returns 404 for a missing question, then 403 when `CanBeEditedBy(user.Id, user.IsAdmin)` is false. Both checks live there instead of using `[Required]` for the 404, so their order is visible in one place.
  - `Put(request, question, ...)` resolves the tags (unknown slugs: 400 `ValidationProblem`, same as `CreateQuestion`), calls `question.Edit` and `SaveChangesAsync`.
- **Status order:** 401 (auth middleware), then 400 from FluentValidation, then 404, 403, 409 (stale version), and the unknown-tag 400. Validation runs before `LoadAsync`, so an invalid body gets 400 even for a missing question or a non-author (seen in testing). Accepted: it reveals nothing, since questions are public anyway, and it saves a database round trip for bad input.
- **The 403 is a `ProblemDetails` built in `Validate`** with `Problems.FromError(Question.Errors.EditForbidden)` (`question.edit_forbidden`, kind `Forbidden`), the same shape as `DomainExceptionHandler` (`detail` plus a `code` extension). Returned, not thrown: a missing permission is an expected outcome, not an exception.
- **204, not 200 with the question:** a `QuestionDetail` needs the projection (score, answer count) that `GetQuestionById` already does, so the client refetches or invalidates its query instead. Step 4 turns the return into `(NoContent, QuestionEdited)`.
- **Tag resolution and the unknown-tag 400 are shared helpers** since 2026-11-18 (see "Shared helpers" below). The validator rules for title, body and tags are still copied from `CreateQuestion`.
- **Concurrency:** solved with a version in the body, see "Concurrency" below.

## Shared helpers (2026-11-18)
- **`Features/Shared/TagLookup.FindBySlugsAsync(db, slugs, ct)`** normalizes the slugs, drops duplicates, loads the matching tags (tracked) in one query and returns `TagLookupResult(Tags, MissingSlugs)` with `HasMissing` and `MissingMessages` ("Tag 'x' does not exist."). Missing slugs are sorted, so the message order is stable. Used by `CreateQuestion` and `EditQuestion`. A static helper taking the context, not a registered service: endpoints keep method injection and Wolverine has nothing new to construct.
- **`Infrastructure/Problems`**: `Validation(key, messages)` builds the 400 `ValidationProblem` with the same shape as the FluentValidation middleware's (pass the key with `nameof`); `FromError(DomainError)` builds a `ProblemDetails` with the error's status, `detail` and `code`, for expected failures an endpoint returns instead of throwing (403, 409); `StatusCodeFor(DomainErrorKind)` is the one mapping from kind to status, now also used by `DomainExceptionHandler`.
- **Rule of thumb:** a failure the endpoint expects (no permission, a stale version, an unknown tag) is returned with `Problems`; a rule the domain enforces is thrown as a `DomainException` and mapped by the handler. Both give the same body.

## Concurrency (2026-11-18)
**Problem:** two people edit the same question; the second save silently overwrites the first ("lost update"). This mostly happens across think time (A opens the edit form, B saves, A saves minutes later), not within one request.

**Chosen: optimistic concurrency with a version in the body.**
- **The version is Postgres's `xmin`.** `Question` implements `Common/IVersioned` (`uint Version`), mapped with `builder.Property(q => q.Version).IsRowVersion()`; Npgsql maps a `uint` row version to the `xmin` system column, which Postgres changes on every update of the row. No column is added and nothing in the code sets it. EF reads it back after an INSERT or UPDATE (`RETURNING xmin`), so `CreateQuestionResponse` already has it.
- **Reads return it, writes send it back:** `QuestionDetail.Version` and `CreateQuestionResponse.Version`; `EditQuestionRequest.Version` is required (`NotEmpty`: a missing field binds to 0, which Postgres never uses as an xmin).
- **Two checks, one answer (409, `code` `concurrency.stale_version`):**
  1. `Validate` compares the sent version with the loaded one (`question.IsStale(request.Version)`) and returns `Problems.FromError(Concurrency.StaleVersion)`. This is the think-time case and the common one.
  2. EF adds `AND xmin = <loaded version>` to the UPDATE (the tracked entity keeps the loaded value), so a write that lands between `LoadAsync` and `SaveChangesAsync` throws `DbUpdateConcurrencyException`, and `Infrastructure/ConcurrencyExceptionHandler` turns it into the same 409.
- **The client's job on 409:** reload the question, show the newer version, let the user apply their change again. Nothing is merged on the server.

**Why not the alternatives:**
- **`ETag` / `If-Match` with 412** is the HTTP-native way, but `If-Match` uses strong comparison, and a strong ETag promises a byte-identical representation. `QuestionDetail` includes `Score` and `AnswersCount`, which change without the question row (and its xmin) changing, so the ETag would be a lie or would have to be weak, and weak ETags never match `If-Match`. The version in the body is the version of the editable row, not of the representation, so it stays honest. Revisit if HTTP caching (`If-None-Match`) comes in with the gateway.
- **A version column incremented by the domain** (`Version++` in `Edit`): portable, but every mutating method must remember it, and it adds a column. `xmin` is free and cannot be forgotten. Cost: tied to Postgres, and `xmin` changes on *any* update of the row (later, for example, a view count or accepted-answer change would also invalidate an open edit form). Revisit if that becomes annoying.
- **Pessimistic locking** (`SELECT ... FOR UPDATE`) only covers one request, not think time.

**For the other cases (how to apply it):** make the entity implement `IVersioned` and map `Version` with `IsRowVersion()` (add an empty migration, see the gotcha); put `Version` in its read DTO and its write request (`NotEmpty`); in the endpoint, load the entity tracked and add `if (entity.IsStale(request.Version)) return Problems.FromError(Concurrency.StaleVersion);` to `Validate` after the 404 and 403. The exception handler already covers the race. Used by `EditQuestion` (version in the body) and `DeleteQuestion` (version in the query string, decided 2026-11-18). Next users: `EditAnswer`, `AcceptAnswer`. `Answer` implements `IVersioned` since 2026-11-20. Creating something never takes a version (see "CreateAnswer").

**Only covers rows EF updates:** changing only a question's tags would write `question_tags` rows and not touch `questions`, so xmin would not be checked. `Question.Edit` always sets `UpdatedAt`, so today the row is always updated.

## DeleteQuestion (2026-11-18)
`DeleteQuestion` (`Features/Questions/DeleteQuestion.cs`) is written, tested by hand and on `main` (`b67c986`).

- **`DELETE /api/questions/{id:guid}?version=N`, `[Authorize]`, 204.** Author or admin (`CanBeEditedBy`, 403 `question.delete_forbidden`), then the version check (409 `concurrency.stale_version`), all in `Validate` like `EditQuestion`. Status order: 401, 400 (missing or unparseable `version`), 404, 403, 409.
- **Version in the query string, not the body** (decided 2026-11-18): a body on DELETE has no defined meaning in HTTP, and some clients and proxies drop it. `DeleteQuestionQuery` is a `[FromQuery]` class with a validator (`NotEmpty`), the same pattern as `GetQuestionsQuery`; `?version=abc` is a 400 from `RejectUnparseableQueryValues`.
- **Hard delete, cascaded by Postgres** (as planned in `docs/architecture.md`: answers live in the question's aggregate). `LoadAsync` loads only the question row, so EF issues one `DELETE FROM questions ... AND xmin = @version` and the database removes answers, answer votes, question votes and the `question_tags` links. Only the links: rows in `tags` are master data and stay. Not loading the answers matters: EF would delete loaded dependents first, and deleting the accepted answer while the question still points at it breaks `fk_questions_accepted_answer` (RESTRICT).
- **Open product point:** anyone who may delete can delete a question with other people's answers, including an accepted one. Stack Overflow blocks that for the author (only moderators can) or soft-deletes. Candidates: a domain rule (author may only delete without answers, 409 `Conflict` otherwise; admin always), or soft delete (`DeletedAt`, filtered out of reads). Decide with the Answers slice, when answers can exist. **Leaning (2026-11-18): soft delete.** People who answered or voted may expect to come back to the question, and a soft-deleted question can still be read (or hidden) while every edit is refused. Not decided yet.

## CreateAnswer (2026-11-20)
`CreateAnswer` (`Features/Answers/CreateAnswer.cs`) is written by the user, tested by hand and on `main` (`2e031dd`).

- **`POST /api/questions/{id:guid}/answers`, `[Authorize]`, 201 Created.** Any signed-in user may answer, including the question's author (allowed on purpose, like Stack Overflow). `LoadAsync` loads the question row only (no `Include`), `Validate` returns 404 when it is missing, and `Post` calls `question.AddAnswer(...)` (the `Answer` constructor is `internal`, so the aggregate is the way in). Status order: 401, 400 (validator), 404.
- **The route is the plural collection** (`/answers`), matching the nested-routes rule in "`GetQuestions`".
- **201 with the answer in the body, not 204 or 200** (decided 2026-11-20): the server creates the id, `CreatedAt` and `Version`, so a 204 would make the client refetch the question to show the answer; a 200 hides that something was created and has no `Location`. It is also the shape step 4 needs: `(Created<CreateAnswerResponse>, AnswerPosted)`.
- **`Location` is `/api/answers/{answerId}`:** answer ids are unique on their own, so later answer routes (edit, delete, accept) can be flat. No `GET /api/answers/{id}` exists yet, so the `Location` points at nothing for now (accepted).
- **The response carries `Version`** (read back by EF from the INSERT), because `EditAnswer` will need it.
- **No version in the request** (decided 2026-11-20): optimistic concurrency prevents lost updates, and adding an answer is an INSERT into `answers` that overwrites nothing. A check against the question's version would reject an answer whenever the author fixed a typo meanwhile, and EF never puts the question's `xmin` into the INSERT anyway, so only half of the check would exist. ## Gotchas already hit
- **Wolverine takes the loaded entity as the request body** (hit 2026-11-18 on `DELETE`): when the endpoint method has no JSON request type, Wolverine 6 treats its first complex parameter as the body, here the `Question` that `LoadAsync` produces, so every call was 400 "Invalid JSON format". Mark it `[NotBody]`. `EditQuestion` never hit it because its first parameter is the request.
- **`[FromQuery]` belongs on the endpoint method only:** put on both the endpoint method and `Validate`, Wolverine generated the query binding twice and the endpoint failed to compile on the first request (500, `CS0128` in the log). Bind it on the endpoint method (which also makes the FluentValidation middleware validate it) and take the same type in `Validate` without the attribute; Wolverine passes the same variable.
- **Npgsql generates `AddColumn("xmin")` when a row version is added to an existing table** (hit 2026-11-18): Postgres rejects it ("column name "xmin" conflicts with a system column name"). Npgsql only omits it when the table is created in the same migration. Keep the migration, for the model snapshot, but empty its `Up` and `Down` (see `20261118235518_AddQuestionVersion`), or remove only the `xmin` lines when the migration also changes other columns (hit again 2026-11-20, `20261120131957_AddAnswerMissingColumns`).
- **A child added through a navigation is not inserted when its key is "generated" but already set** (caught in review 2026-11-20): EF gives a `Guid` key `ValueGeneratedOnAdd` by convention. The domain sets the key with `Guid.CreateVersion7()`, so when change detection finds the new `Answer` in `question.Answers` with a key already set, it assumes the row exists and does not mark it Added. The save then fails or does nothing, and an UPDATE that matches 0 rows surfaces as a misleading 409 from `ConcurrencyExceptionHandler`. Fix: `.ValueGeneratedNever()` on every domain-generated id (done on `Question.Id` and `Answer.Id`), which tells EF the truth. Alternative: `db.Answers.Add(answer)` in each endpoint.
- **`psql` inside the Postgres container needs the password:** `docker exec -i <container> sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" psql -U postgres -d questions-db'` reads it from the container's environment without printing it.
- **Keycloak is served over HTTPS since Aspire 17** (hit 2026-11-18): a token request to `http://localhost:6001` gets no answer; use `https://localhost:6001/realms/cortex/protocol/openid-connect/token` with the dev certificate (`curl -k` in scripts). The container's own port is 8443.
- **FluentValidation runs before `LoadAsync`:** an invalid body is a 400 even when the question does not exist or the caller may not edit it. Do not expect a 404 or 403 from a test that also sends a bad body.
- **Wolverine 6 wouldn't start** until `WolverineFx.RuntimeCompilation` was added and enabled with `opts.UseRuntimeCompilation()`.
- **Access tokens lacked `sub`** until the `basic` client scope was added to the clients. Now in the realm file.
- **Roles:** the built-in roles scope was removed in favour of a flat `roles` mapper on `cortex-web` and `cortex-dev-tools`, so read `roles`, not `realm_access.roles`.
- **Realm edits need a fresh volume:** Keycloak skips the import when the realm already exists, and the AppHost persists Keycloak in the `keycloak-data` volume. After editing `cortex-realm.json`, delete that volume (or the realm) and restart, otherwise the change is silently ignored.
- **`dotnet run` on the AppHost failed while watch was on:** with `AspireUseCliBundle`, `dotnet run --project src/Cortex.AppHost` delegates to `aspire run --no-build`, which the CLI rejects while `defaultWatchEnabled` is true in `aspire.config.json` ("The --no-build option cannot be used when watch mode is enabled"). Watch is now off (see the Aspire 17 decision), but `dotnet run` has not been retried; keep using `aspire run` from the repo root.
- **`aspire update` failed to restore on the 13.6.5 to 17.0 upgrade (2026-11-18):** `Aspire.Keycloak.Authentication` 17 needs `Microsoft.AspNetCore.Authentication.JwtBearer` 10.0.15 or later, and ServiceDefaults pinned 10.0.14, so NuGet reported a downgrade (`NU1605`, an error by default). The CLI only says "failed to restore"; run `dotnet restore` on the AppHost to see the real error. The pin is now 10.0.15 and has to follow each Aspire update.
- **The test project sees an older EF Core than the service runs** (hit 2026-11-20, `MSB3277`): the service gets EF Core 10.0.15 through `Microsoft.EntityFrameworkCore.Design`, which is `PrivateAssets`, so a project referencing the service only sees 10.0.14 from `Aspire.Npgsql.EntityFrameworkCore.PostgreSQL` 13.6.5 (no 17.x exists yet). The test project pins `Microsoft.EntityFrameworkCore.Relational` 10.0.15; keep it in step with the service's Design package.
- **First start logs one EF error:** `Failed executing DbCommand ... FROM "__EFMigrationsHistory"` appears once on an empty database, because EF queries the history table before creating it. It is harmless.
- **Checking the EF model without a database:** from the service folder, `env "ConnectionStrings__questions-db=Host=localhost;Database=x;Username=x;Password=x" dotnet ef dbcontext script` builds the model and prints the schema. Without the dummy connection string the design-time host fails.
- **A collection navigation with no inverse is one-to-many by convention:** `Question.Tags` needed an explicit `HasMany().WithMany()`, and explicit FK names in `UsingEntity` to get `tag_id` instead of `tags_id`.
- **A new endpoint needs a restart:** an endpoint file added while the AppHost was running under `aspire start` returned 404 until the AppHost was restarted.
- **A project resource needs `WithHttpHealthCheck` for `aspire wait` to mean "ready":** without one, "healthy" only means the process started, and a script that queried the database right after `aspire wait question-service` saw the state from before migrations and seeding. The question service now has `.WithHttpHealthCheck("/health")` in the AppHost (verified 2026-11-13: the wait returns after the service is listening). Give every new service the same.
- **Postgres password and volume go together:** Aspire generates the Postgres password once and keeps it in the AppHost's user secrets, while the data lives in the `postgres-data` volume. If one is reset without the other, logins fail; delete the volume to start clean.
- **Aspire's `AddNpgsqlDbContext` breaks Wolverine 6 endpoints that take the `DbContext`** (hit 2026-11-14 on `POST /api/questions`): the request fails with `InvalidServiceLocationException ... 'opaque' lambda factory with the Scoped lifetime`. Wolverine generates the endpoint code and wants to construct the context inline; Aspire registers it through a factory lambda, which Wolverine cannot see into, so it would have to ask the container at runtime (service location). Wolverine 5 allowed that with a warning; Wolverine 6 defaults to `ServiceLocationPolicy.NotAllowed`. Fix: register the context with `builder.Services.AddDbContext<T>(..., optionsLifetime: ServiceLifetime.Singleton)` (the lifetime the Wolverine EF Core docs recommend) and call `builder.EnrichNpgsqlDbContext<T>()` after it for Aspire's health check, retries and telemetry. Trade-off: no context pooling. Rejected alternative: `opts.CodeGeneration.AlwaysUseServiceLocationFor<T>()`, one line but it keeps service location, which the docs warn can break scoping once the outbox is in. Step 4 replaces the registration with `AddDbContextWithWolverineIntegration`, which has the same shape. Do the same in every new service that has a `DbContext`.
- **FluentValidation's `Must` has a useless default message** ("The specified condition was not met for 'Tag Slugs'."). Always give it one; `WithError(DomainError)` does.
- **FluentValidation error codes do not reach the client:** Wolverine's problem-details middleware emits only property names and messages, so the message is all a client gets from a validator failure. Codes only appear in `DomainExceptionHandler` responses.
- **FluentValidation keeps running a rule chain after a failure:** `NotNull().Must(x => x.Count ...)` throws on null. Use `.Cascade(CascadeMode.Stop)` or a null-safe predicate.
- **`abstract` on a request type breaks the endpoint at runtime** (hit 2026-11-18): Wolverine only binds a concrete type from the JSON body, so it looked for `CreateQuestionRequest` elsewhere and code generation failed with `UnResolvableVariableException` on the first request (500). It builds fine. Request and query types are `sealed`.
- **`PagedResult` from `System.Linq.Dynamic.Core` is not ours** (hit 2026-11-18): the package comes in transitively through JasperFx, so the IDE offers its types. Its `PagedResult` holds an unexecuted `IQueryable` that the JSON serializer would run synchronously. Use `Features/Shared/PagedResponse<T>` with a materialised list.
- **Unbounded `?page=` overflows `Skip`:** `(Page - 1) * PageSize` past `int.MaxValue` goes negative and `Skip` throws (500). `PagedQuery.MaxPage` caps it, so it is a 400.
- **A malformed route id is a 404, not a 400** (seen 2026-11-18): `/api/questions/abc` does not parse as the endpoint's `Guid id`, so Wolverine treats the route as not matched and returns 404 even without a `{id:guid}` constraint. The route now has the constraint anyway, which makes the rule visible on the attribute. It differs from query strings, where `?page=abc` is a 400 because of `RejectUnparseableQueryValues`. That fits REST (no resource has that id), but a client cannot tell "bad id" from "no such question".
- **`Include` does nothing in a projection:** once a query ends in `Select(...)`, the projection decides what loads and EF ignores `Include`. A leftover `Include` before a `Select` only suggests the opposite of the projection rule.
- **Validation error keys are the C# property names** (`TagSlugs`, not `tagSlugs`). A hand-built `ValidationProblem` should use `nameof(...)` so both 400s agree.
- **The validator answers before the domain is reached:** the FluentValidation middleware short-circuits the request, so a request that breaks both a validator rule and a rule only the domain checks returns only the validator's errors (seen 2026-11-14: six tags plus an empty title, with the title rule disabled, reported only the tag count). The domain error appears once the validator passes.
